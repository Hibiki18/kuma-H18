# 游戏画面运行时独立窗口需求文档

> 文档状态：需求草案（进入完整开发前必须通过技术 PoC）  
> 适用仓库：kuma  
> 目标平台：Windows 10 / Windows 11  
> 编写日期：2026-08-29

## 1. 背景

kuma 当前把舰 C 游戏页以内嵌 `<webview>` 的形式放在工作台中央，左、右、下三坞与游戏画面共享一个主窗口。小屏幕电脑上，游戏画面与辅助面板会争抢有限空间；即使折叠坞位，用户也很难同时获得合适的游戏尺寸与足够的工作台可视面积。

本需求增加“独立游戏窗口”模式，并允许用户在游戏运行过程中随时把游戏画面拆出或收回。切换不是重新打开一个游戏页，而是迁移同一个正在运行的游戏宿主：登录态、当前页面、音频、网络监听和本地记录链路均须连续。

## 2. 可行性结论

### 2.1 结论

需求**有条件可行，整体复杂度高**。

Electron 提供 `View.addChildView`、`View.removeChildView` 与 `WebContentsView`，允许主进程组合原生视图；`BaseWindow` 关闭时也不会自动销毁其 `WebContentsView.webContents`。因此，可以让主进程持有一份长期存活的游戏宿主视图，并在主窗口与独立窗口之间更换父容器，而不主动销毁游戏会话。

但当前项目使用的是“主渲染页中的 `<webview>`”，Electron 官方同时明确提示 `<webview>` 的渲染、导航与事件路由存在稳定性风险。官方文档没有明确承诺“包含嵌套 `<webview>` 的 `WebContentsView` 可跨两个顶层窗口反复迁移且 guest 永不重建”。所以，本需求不能直接进入完整实现，必须先用项目实际 Electron 版本和 Windows 环境完成第 12 节的 PoC。

### 2.2 官方能力依据

- [`View`](https://www.electronjs.org/docs/latest/api/view)：提供 `addChildView`、`removeChildView` 与边界设置能力。
- [`WebContentsView`](https://www.electronjs.org/docs/latest/api/web-contents-view)：一个 `WebContents` 同一时刻只能呈现在一个 `WebContentsView` 中，可由主进程控制。
- [`BaseWindow`](https://www.electronjs.org/docs/latest/api/base-window)：窗口关闭不会自动销毁附加的 `WebContentsView.webContents`，要求应用自行管理生命周期。
- [`<webview>` Tag`](https://www.electronjs.org/docs/latest/api/webview-tag)：官方提示该能力受 Chromium 架构变化影响，并建议评估 `WebContentsView` 等替代方案。

## 3. 产品目标

1. 小屏幕用户可以把游戏画面移到单独窗口，让工作台使用主窗口的全部可用空间。
2. 游戏运行期间可以随时“拆出游戏”或“收回工作台”，不要求退出应用或重启。
3. 切换前后保持同一份游戏会话，不重新登录、不刷新页面、不重放当前音频。
4. API 监听、状态归并、事件账本、通知规则与截图等现有能力在两种模式下行为一致。
5. 默认仍为当前的内嵌模式，不改变未启用该功能的用户体验。

## 4. 非目标

- 不同时显示两份游戏画面，也不提供镜像或画中画模式。
- 不支持同时登录多个游戏账号或启动多个游戏 guest。
- 不在本需求中重做三坞布局、设置中心或通知规则系统。
- 不以升级 Electron、全面移除 `<webview>` 或重写游戏 preload 为顺带目标；若 PoC 证明现架构不可行，应另立迁移需求。
- 不承诺突破游戏本身、Chromium 或操作系统对最小尺寸、媒体播放和输入焦点的限制。

## 5. 术语与核心不变量

| 术语 | 定义 |
|---|---|
| 工作台窗口 | 当前承载顶栏、三坞、设置和各业务模块的主窗口 |
| 游戏宿主 | 由主进程长期持有、内部承载唯一游戏 `<webview>` 及其随行浮层的本地页面 |
| 游戏 guest | 实际加载舰 C 页面的唯一 `<webview>` WebContents |
| 内嵌模式 | 游戏宿主附着在工作台窗口的游戏区域 |
| 独立模式 | 同一个游戏宿主附着在独立游戏窗口 |

实现与验收必须共同维护以下不变量：

1. 应用运行期间最多存在一个有效游戏 guest。
2. 普通模式切换不销毁、不重建游戏宿主或游戏 guest。
3. 同一条游戏 API 响应只进入状态核心和事件账本一次。
4. 通知规则只计算一次，声音、系统通知和推送不因双窗口重复触发。
5. 游戏 preload、会话、代理、缓存与资源替换的安全边界不因窗口模式改变。
6. 切换成功前不持久化目标模式；切换失败时保持或恢复到原模式。

## 6. 用户入口与设置

### 6.1 设置项

在“设置”中新增“游戏窗口模式”：

- `嵌入工作台`：默认值，保持现有布局。
- `独立窗口`：游戏画面显示在单独窗口，工作台释放原游戏区域。

建议配置键：

- `kanso.gameWindow.mode`: `embedded | detached`
- `kanso.gameWindow.bounds`: 独立窗口最后一次正常位置和尺寸

用户修改设置后立即尝试切换，不显示“重启后生效”。只有切换成功才保存新模式。

### 6.2 快速操作

- 内嵌模式下，工作台顶栏提供“拆出游戏”。
- 独立模式下，工作台顶栏提供“收回游戏”和“定位游戏窗口”。
- 独立游戏窗口提供“收回工作台”“刷新”“截图”等与游戏直接相关的操作。
- 不新增默认全局快捷键，避免与游戏和现有 `F9` 专注模式冲突；后续如需快捷键应另行评估。

## 7. 功能需求

### FR-001 默认与持久化

- 新安装或没有该配置时必须使用内嵌模式。
- 应用正常启动时恢复上次成功使用的模式。
- 若独立窗口保存位置不在任何当前显示器工作区内，应回到主显示器可见区域。
- 独立窗口的位置、正常尺寸和最大化状态应独立于工作台窗口保存。

### FR-002 运行中拆出游戏

用户在游戏登录页、母港、出击或战斗等任意运行状态下均可发起拆出操作。成功后必须满足：

- 原游戏 guest 的 WebContents ID 保持不变；
- 不产生主框架导航、刷新或重新登录；
- 独立窗口显示的内容与切换前是同一会话的连续画面；
- 工作台移除原游戏占位，并让三坞/业务区使用释放出的空间；
- 工作台顶栏明确显示游戏当前处于独立窗口。

### FR-003 运行中收回游戏

收回操作是 FR-002 的逆过程。成功后：

- 同一个游戏宿主回到工作台的游戏区域；
- 独立窗口关闭，但游戏 guest 不因该窗口关闭而被销毁；
- 工作台恢复内嵌布局并重新计算游戏显示尺寸；
- 游戏会话与采集链路连续。

### FR-004 切换原子性与防重入

- 状态转换期间禁用重复点击，连续指令只执行一次。
- 重复请求切到当前模式应视为成功的幂等操作。
- 目标窗口或目标父视图未准备好时，不得先销毁源视图。
- 任一步失败时优先回挂源容器并保留原模式，向用户显示可理解的错误提示。
- 不得把“销毁并新建游戏页”作为静默降级方案；需要刷新时必须由用户明确触发。

### FR-005 独立窗口行为

- 窗口标题使用“kuma · 游戏”，任务栏可独立切换。
- 窗口可移动、缩放和最大化；游戏内容始终保持 `1200:720`（5:3）比例，剩余空间用背景留边，不拉伸画面。
- 点击独立游戏窗口的关闭按钮表示“收回工作台”，同时显示/聚焦工作台；不代表退出应用。
- 独立窗口无系统菜单，不允许游戏外链生成无管理的 Electron 裸窗口；现有外链仍交给系统浏览器。
- 独立窗口移到另一台显示器或不同 DPI 的显示器后，应重新计算边界、缩放和点击坐标。

### FR-006 工作台行为

- 独立模式下不能保留一块与原游戏等大的空黑区域；工作台内容应使用释放出的空间。
- 顶栏保留清晰、可键盘操作的游戏状态与找回入口。
- 从托盘恢复或启动第二个应用实例时：工作台应可见；若处于独立模式，游戏窗口也必须保持可定位、可唤回。
- `F9` 仍只表示现有“专注模式”，不得被复用为窗口模式开关。拆出游戏时应退出无实际意义的专注布局，不能留下空白工作台。

### FR-007 游戏随行界面

以下与游戏画面空间或游戏 guest 直接耦合的能力必须随游戏宿主移动，不能被原生视图遮挡：

- 语音字幕与弹幕；
- 游戏加载失败遮罩、错误详情和重试入口；
- 叠加在 `#game-wrapper` 上的通知 toast、横幅或提示；
- 启动欢迎/点亮效果中覆盖游戏区域的部分。

业务规则、事件判断和持久化仍只在工作台现有单一责任方执行。若独立窗口需要展示通知，只传递已经判定好的只读展示事件，不在游戏宿主中再运行一份通知规则。

### FR-008 游戏控制与现有能力

两种模式下均须支持：

- 刷新游戏页、加载失败重试；
- 游戏截图并保存到现有目录；
- 游戏音量、语音字幕、音频自检；
- 试听音频播放时对游戏音量的现有 duck/恢复逻辑；
- 服务器识别、资源缓存替换、代理设置和外链处理；
- guest 崩溃后的现有自愈流程。

控制动作不得通过查询某个窗口内的 `#game-wrapper webview` 来定位唯一游戏实例；应由主进程的游戏宿主管理器统一路由，或通过受控 IPC 请求游戏宿主执行。

### FR-009 托盘与退出

- 启用“关闭到托盘”时，关闭工作台只隐藏工作台；已拆出的游戏窗口继续运行并保持可见。
- 未启用“关闭到托盘”时，关闭工作台沿用当前退出应用语义，独立游戏窗口和游戏 guest 一并有序销毁。
- 从托盘执行“退出艦素”或系统触发真实退出时，必须显式关闭游戏宿主 WebContents、独立窗口和游戏 guest，不能留下 renderer/guest 进程。
- 退出流程只允许执行一次，不能因两个窗口的 `close` 事件形成递归关闭或阻断退出。

### FR-010 异常恢复

- 游戏宿主 renderer 崩溃与游戏 guest 崩溃必须区分记录。
- 单纯切换失败不应触发 guest 崩溃自愈，也不应重建 guest。
- guest 确实崩溃时可以沿用现有“原地重挂”策略，并在当前窗口模式中恢复。
- 工作台 renderer 重载或崩溃时，主进程持有的游戏宿主应尽量继续存活；工作台恢复后重新报告内嵌区域边界或提供找回入口。
- 若宿主已失去两个父容器且回滚失败，应进入明确的恢复态，保留诊断信息并提示用户选择刷新，不得悄悄丢失会话。

## 8. 非功能需求

### NFR-001 连续性

- 正常切换不得触发游戏主框架 `did-start-navigation`、`reload` 或新的 `did-attach-webview`。
- 正常切换前后游戏 guest WebContents ID 与 session 必须一致。
- 切换过程中游戏网络请求监听不得中断、遗漏或重复记账。

### NFR-002 性能与体验

- 在参考开发机上，从用户触发到目标窗口可交互应不超过 1 秒。
- 允许迁移瞬间出现短暂背景帧，但不得出现登录页、白屏长驻或第二份游戏声音。
- 拖动工作台分隔条和缩放独立窗口时，不得按每个鼠标事件同步跨进程调用；需要合帧或防抖。

### NFR-003 安全

- 游戏宿主只加载应用随包的本地入口，远端游戏内容仍放在受限制的唯一 guest 中。
- `will-attach-webview` 必须继续校验受信任 preload，并拒绝第二个或来源异常的 `<webview>`。
- 不得因为多窗口而放宽 `nodeIntegration`、preload 白名单、导航限制或 IPC 发送者校验。
- 新增 IPC 必须校验发送者 WebContents、参数类型和允许的状态转换。

### NFR-004 可维护性

- 主进程必须成为游戏宿主、游戏 guest ID、当前窗口模式和生命周期的唯一所有者。
- 窗口切换使用显式状态机，不依赖散落的布尔值和 DOM 是否存在来推断状态。
- 视图销毁职责只有一个出口；退出路径必须显式释放 `WebContentsView.webContents`。

### NFR-005 可访问性

- 拆出、收回、定位、刷新和截图操作应有可见文本或准确的可访问名称。
- 切换完成或失败后，焦点落在可预期的窗口和控件上；不能把键盘焦点留在已隐藏/已关闭窗口。

## 9. 推荐技术方案

### 9.1 结构

```text
主进程 GameHostManager
├─ 唯一 gameHostView: WebContentsView
│  └─ 本地 game-host.html
│     ├─ 唯一游戏 <webview>
│     ├─ 字幕 / 弹幕
│     ├─ 加载错误遮罩
│     └─ 只读通知展示层
├─ 工作台 BrowserWindow
│  └─ contentView（内嵌模式时挂载 gameHostView）
└─ 独立游戏 BrowserWindow 或 BaseWindow
   └─ contentView（独立模式时挂载同一个 gameHostView）
```

主进程创建一次 `gameHostView`。内嵌模式把它挂到工作台 `contentView` 并按 `#game-area` 上报的 DIP 边界定位；独立模式先准备目标窗口，再从工作台移除并挂到独立窗口。收回时反向执行。

采用本地 `game-host.html` 而不是直接把远端游戏页作为顶层视图，目的是保留现有 `<webview>` preload/iframe 处理，并让字幕、弹幕、加载遮罩等与游戏画面一起迁移。该方案也是 PoC 必须重点验证的风险点。

### 9.2 状态机

```text
EMBEDDED ──detach──> DETACHING ──success──> DETACHED
   ^                    │                       │
   │                 rollback                attach
   │                    │                       v
   └────────────────────┘                  ATTACHING
   ^                                            │
   └────────────────────success─────────────────┘

任一迁移阶段失去父容器且回滚失败 ──> RECOVERING
```

- `EMBEDDED` / `DETACHED` 才允许接受新切换命令。
- `DETACHING` / `ATTACHING` 中的重复命令被合并或拒绝。
- 只有进入稳定目标态后才保存 `kanso.gameWindow.mode`。
- `RECOVERING` 不得自动新建 guest；先尝试重新挂载现存宿主，再提示用户采取显式恢复动作。

### 9.3 边界同步

工作台 renderer 通过 `ResizeObserver`、窗口缩放和布局变化上报游戏区域矩形，主进程把 CSS 像素换算为 Electron 视图使用的 DIP 后调用 `setBounds`。必须覆盖：

- UI 缩放；
- Windows 显示缩放 100% / 125% / 150% / 200%；
- 主窗口最大化/恢复；
- 左右/底部分隔条拖动；
- 跨显示器移动。

当前分隔条拖动期间依赖 CSS `transform` 缩放 `<webview>`；原生 `WebContentsView` 不受主页面 DOM transform 控制，因此需改为对视图边界做合帧/节流更新，并在拖动结束后执行一次精确缩放。

## 10. 当前源码影响面

| 层级 | 已确认的现状 | 本需求影响 |
|---|---|---|
| `src/main/index.ts` | 主窗口监听 `will-attach-webview` / `did-attach-webview`，局部变量保存 `gameWebContentsId` | 抽出主进程 GameHostManager，统一视图、guest、安全、窗口和退出生命周期 |
| `src/main/game-api-broadcaster.ts` | IPC 只接受 `webview` 类型发送者 | 保持唯一 guest 身份校验，确认迁移前后类型与 ID 不变 |
| `src/main/kcs-resource.ts` | 按 `gameWebContentsId` 识别并替换游戏资源 | ID 归 GameHostManager 所有，切换不得清空或重复登记 |
| `src/main/quit-guard.ts` | 按当前主窗口 + webview guest 生命周期处理残留进程 | 增加游戏宿主视图和独立窗口的显式关闭顺序 |
| `src/renderer/index.ts` | 创建 webview，并直接处理刷新、截图、崩溃重挂、缩放和 `F9` | 游戏 DOM 与控制职责拆分；工作台只发命令和上报边界 |
| `src/renderer/index.html` | `#game-wrapper` 同时承载游戏、字幕、弹幕和遮罩 | 游戏随行 DOM 移到 `game-host.html`，工作台独立模式释放游戏区域 |
| `src/renderer/voice-subtitle.ts` | 通过 `#game-wrapper webview` 查询 guest 并操作字幕 DOM | 在游戏宿主内运行，或改为通过单一游戏控制通道查询 |
| `src/renderer/modules/yu.ts` | 音频自检直接查询工作台内 webview | 改走 GameHostManager/宿主 IPC，窗口模式透明 |
| `src/renderer/modules/lg.ts` | 部分 toast 挂在 `#game-wrapper` | 规则仍只执行一次，展示结果通过 IPC 镜像给游戏宿主 |
| `src/renderer/launch-glow.ts` | 启动效果依赖 `#game-area` | 区分工作台装饰与随游戏迁移的覆盖层 |

以上为需求阶段已确认的直接影响面；实施前仍需用全仓调用检索补齐间接消费者。

## 11. 关键产品规则

1. “独立窗口”是显示模式，不是第二游戏实例。
2. 独立窗口的 X 等同“收回”，工作台窗口的 X 继续遵守现有退出/托盘配置。
3. 切换可以在战斗中发起；产品不增加“仅母港可切换”的人为限制。
4. 切换失败不改变设置、不刷新游戏、不伪装成功。
5. 默认内嵌，现有用户不需要迁移数据库或重新配置代理、声音、通知和布局。
6. 工作台负责业务规则和持久化，游戏宿主负责游戏画面及其随行展示；不能形成两套状态核心。

## 12. 开发前技术 PoC 闸门

### 12.1 PoC 范围

使用仓库当前声明的 Electron `^43.2.0`，并记录锁文件实际解析版本，在 Windows 10 和 Windows 11 上构造最小实现：

1. 一个长期存活的 `WebContentsView` 加载本地宿主页；
2. 宿主页内创建与生产配置一致的唯一 `<webview>` 和 preload；
3. 主窗口与独立窗口反复通过 `removeChildView` / `addChildView` 迁移同一个宿主视图；
4. 记录宿主 ID、guest ID、导航事件、attach/destroy 事件、音频状态与模拟 API 流。

### 12.2 必须通过的项目

- 连续往返切换 100 次，宿主 WebContents ID 与游戏 guest WebContents ID 均不变化；
- 切换不产生新的 `did-attach-webview`、主框架导航、reload 或 preload 重装；
- 持续网络请求在切换前后都可被监听，每条只记录一次；
- 正在播放的音频不从头播放，不出现第二路声音；
- 鼠标、键盘、滚轮、文本输入和焦点在两个方向切换后都正常；
- 字幕/遮罩层渲染顺序和点击命中正确，不被原生视图覆盖；
- 100% / 125% / 150% / 200% DPI 以及双屏异 DPI 下，画面比例、清晰度和点击坐标正确；
- 关闭独立窗口可回挂，关闭应用无残留 renderer/guest 进程；
- 人为制造目标窗口创建失败与挂载失败时能回滚，现有 guest 不被销毁。

### 12.3 闸门结论

- **全部通过**：可以按本需求进入完整实现。
- **guest 被重建、导航或会话中断**：当前“宿主视图包裹 `<webview>`”方案不可用于无刷新切换，应暂停开发，另行评估把游戏本体迁移为直接 `WebContentsView`。
- **只有 DPI、焦点、边界或浮层问题**：先形成可验证的修复方案，再进入业务迁移；不得把已知缺陷留到完整实现后兜底。
- **PoC 失败时不接受自动刷新降级**：这会违反“运行中随时切换且保持会话”的核心需求，必须由产品重新选择范围。

## 13. 验收标准

### AC-001 首次使用

给定用户没有游戏窗口配置，启动应用时游戏仍内嵌在工作台，现有布局、登录和网络采集行为不变。

### AC-002 战斗中拆出

给定游戏已登录并持续产生 API 请求，用户点击“拆出游戏”后，1 秒内独立窗口可操作；页面不刷新、guest ID 不变、前后请求连续且账本无重复。

### AC-003 收回

给定游戏处于独立窗口，用户点击“收回工作台”或关闭独立窗口后，同一画面回到工作台，当前页面、音频进度和登录态保持。

### AC-004 反复切换

给定同一次应用运行，用户连续往返切换 100 次，不新增第二个游戏 guest、不发生会话重建、不残留隐藏游戏窗口。

### AC-005 小屏幕收益

给定 1366×768、Windows 显示缩放 100% 与 125% 的环境，独立模式下工作台不保留原游戏大块占位，各模块仍可滚动和操作；独立游戏窗口完整显示且不拉伸。

### AC-006 双屏与 DPI

给定两台 DPI 不同的显示器，用户把独立窗口跨屏移动、缩放和最大化，游戏画面比例、清晰度、点击位置和字幕位置均正确；拔掉副屏后窗口回到可见区域。

### AC-007 现有能力

给定任一窗口模式，刷新、重试、截图、字幕、弹幕、音量、自检、试听压音、通知、代理和资源替换均能完成，且没有双份通知或声音。

### AC-008 托盘与退出

给定独立模式，关闭到托盘只隐藏工作台而不关游戏；从托盘真实退出后，两个窗口和所有宿主/guest 进程均退出。

### AC-009 故障回滚

给定目标窗口创建或视图挂载被测试桩强制失败，操作返回失败并保持原模式，设置值不变，游戏页不刷新，用户能继续操作。

### AC-010 安全回归

构造第二个 `<webview>`、伪造 preload、非法 IPC 发送者和非法状态参数时均被拒绝；正常游戏 guest 仍可工作。

## 14. 验证计划

### 14.1 静态与自动化验证

- TypeScript 类型检查与生产构建；
- 状态机单元测试：合法转换、幂等、防重入、失败回滚、退出态；
- 边界换算单元测试：DIP、UI 缩放、比例留边、异常尺寸；
- IPC 权限测试：发送者、参数、重复命令、销毁后的请求；
- 通知/API 测试：同一输入只进入规则和账本一次；
- 退出测试：所有窗口顺序、托盘拦截与显式释放只执行一次。

### 14.2 Windows 运行时验证

- 1366×768 单屏、1080p/2K 双屏、100%～200% DPI；
- 登录页、母港、编成、出击、战斗、播放语音时双向切换；
- 独立窗口移动、缩放、最大化、关闭、系统休眠/恢复、显示器拔插；
- 工作台最小化/关闭到托盘、托盘恢复、第二实例唤回、系统关机退出；
- 工作台 renderer 崩溃、游戏宿主 renderer 崩溃、游戏 guest 崩溃分别验证；
- 使用受控请求序列对比切换前后的 API 数量、顺序、账本条目和通知次数。

生产构建成功只能证明静态产物可生成；“同一会话无刷新迁移”必须以 Windows 真机运行结果为准。

## 15. 实施阶段

1. **阶段 0：PoC 闸门**——只验证跨窗口迁移、ID、会话、输入、音频与 DPI，不接业务 UI。
2. **阶段 1：宿主隔离**——先在内嵌模式使用独立 game-host，迁移字幕、遮罩和控制通道，保证行为与现状一致。
3. **阶段 2：运行时切换**——实现 GameHostManager、状态机、独立窗口、边界同步和设置入口。
4. **阶段 3：业务兼容**——迁移 toast/横幅、音频自检、截图、试听压音、托盘和退出链路。
5. **阶段 4：回归与发布**——完成自动化、Windows 真机、小屏/多屏、崩溃与退出验证，再决定是否默认展示入口。

每一阶段都应保持默认内嵌路径可运行；阶段 0 未通过时停止后续开发。

## 16. 风险清单

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 嵌套 `<webview>` 跨父窗口迁移未被官方明确保证 | guest 重建、白屏或事件丢失 | 阶段 0 强制 PoC；失败则另立直接 WebContentsView 迁移方案 |
| 原生 WebContentsView 位于工作台 DOM 之上 | 字幕、遮罩、toast 被遮挡 | 将游戏随行 DOM 移入本地宿主页 |
| 当前控制代码直接查询工作台内 webview | 独立模式下刷新、截图、自检失效 | 主进程统一持有 ID，控制通过受控 IPC 路由 |
| 通知展示迁移时复制业务初始化 | 双通知、双声音、双账本 | 工作台保持唯一规则所有者，只发送已判定展示事件 |
| 分隔条 CSS transform 不再作用于原生视图 | 拖动卡顿、边界错位 | 合帧/节流 setBounds，松手精确缩放，真机测 DPI |
| 多窗口关闭与托盘逻辑互相触发 | 无法退出或残留 guest | 明确“收回”和“真实退出”两条路径，集中生命周期所有权 |
| gameHostView 未显式关闭 | 内存泄漏、残留进程 | 唯一销毁出口，并纳入 quit-guard 测试 |

## 17. 发布条件

只有同时满足以下条件，功能才可进入正式发布：

1. 第 12 节 PoC 全部通过并保存可复现实验记录；
2. 第 13 节验收标准全部通过；
3. 默认内嵌模式的现有功能无回归；
4. Windows 小屏、多屏、异 DPI 和退出链路完成真机验证；
5. 未引入第二份游戏 guest、重复 API 账本或重复通知；
6. 已记录实际 Electron 锁定版本与已知平台限制。
