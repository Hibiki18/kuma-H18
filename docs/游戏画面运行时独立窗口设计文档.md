> 目标平台：Windows 10 / Windows 11

> 编写日期：2026-08-29

## 1. 设计结论

采用“**主进程持有唯一游戏宿主，宿主视图在两个顶层窗口之间迁移**”的方案：

- 主进程创建且只创建一个 `WebContentsView`，加载本地 `game-host.html`；
- `game-host.html` 内创建唯一游戏 `<webview>`，并承载字幕、弹幕、加载遮罩和只读通知展示层；
- 内嵌模式把同一个宿主视图挂到工作台 `BrowserWindow.contentView`；
- 独立模式把同一个宿主视图挂到独立游戏 `BrowserWindow.contentView`；
- 工作台继续独占数据核心、通知判定、事件账本与业务导航，游戏宿主不初始化第二套业务模块；
- 游戏刷新、截图、音频自检、试听压音等操作统一通过主进程 `GameHostManager` 路由，不再从工作台 DOM 查询 `<webview>`。

Electron 官方 API 已提供本方案所需的基础拼装能力：`View` 支持增加、移除子视图和设置相对父级的边界，`BrowserWindow` 继承 `BaseWindow` 并具有 `contentView`，`WebContentsView` 持有可长期交互的 `webContents`。官方同时要求应用显式管理附加视图的 `webContents` 生命周期，不能依赖窗口关闭自动释放。参考：[View](https://www.electronjs.org/docs/latest/api/view)、[WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view)、[BaseWindow](https://www.electronjs.org/docs/latest/api/base-window)、[BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window)。

上述 API 只证明“原生视图可组合、可移除、可重新挂载”，**不证明嵌套 `<webview>` 的宿主页跨窗口迁移后 guest 必然不重建**。因此本设计仍以第 14 节 PoC 为硬闸门，PoC 未通过时不得进入阶段 1～4。

## 2. 现状与改造边界

### 2.1 已核对的当前调用链

当前实现的核心链路如下：

```text
src/main/index.ts 创建工作台 BrowserWindow（webviewTag: true）
  └─ src/renderer/index.ts 在 #game-wrapper 创建游戏 <webview>
      ├─ assets/preload/webview-preload.js 注入监听、资源与音频钩子
      ├─ kanso:game-api → src/main/game-api-broadcaster.ts
      │   └─ 工作台 renderer 的 kernel / 各业务模块消费
      ├─ gameWebContentsId → src/main/kcs-resource.ts
      └─ 工作台 DOM 直接执行 reload / capture / audio stats / crash remount
```

已确认的耦合点：

| 位置 | 当前职责 | 设计后的归属 |
|---|---|---|
| `src/main/index.ts` | 创建主窗口；在主窗口上监听 `will-attach-webview` / `did-attach-webview`；局部保存 guest ID；转发试听压音 | 窗口装配入口；具体游戏生命周期交给 `GameHostManager` |
| `src/renderer/index.ts` | 创建/重建 webview；缩放；刷新；截图；分隔条拖动；专注模式 | 只保留工作台布局、状态入口和内嵌区域边界上报 |
| `src/renderer/index.html` | `#game-wrapper` 同时承载 webview、字幕、弹幕、错误遮罩 | 保留 `#game-area` 为原生视图占位；随游戏 DOM 移入 `game-host.html` |
| `src/main/game-api-broadcaster.ts` | 接受任意 `webview` 类型发送者的 API IPC | 只接受 `GameHostManager` 登记的唯一 guest ID |
| `src/main/kcs-resource.ts` | 保存 guest ID，按 ID 识别资源请求和档案 IPC | ID 来源改为 manager；原有资源规则和 session 不变 |
| `src/renderer/voice-subtitle.ts` | 同时做台词解析、状态判定、guest 音频时长查询和 DOM 展示 | 拆成工作台“解析控制器”与宿主“纯展示器” |
| `src/renderer/modules/lg.ts` | 通知判定、落账、声音、系统通知、推送和 toast DOM 都在工作台 | 判定与副作用留在工作台；只把已经判定的 toast 展示命令送到宿主 |
| `src/renderer/modules/yu.ts` | 音频自检直接查 `#game-wrapper webview` | 经受控 IPC 调用 manager 的只读音频统计命令 |
| `src/main/tray.ts` | 只认识工作台窗口 | 恢复应用时同时保证独立游戏窗口可见、可定位 |
| `src/main/quit-guard.ts` | 收割 renderer PID，兜底清理孤儿 guest | 保留 OS 级兜底；在它之前增加 manager 的显式有序释放 |

`package-lock.json` 当前锁定 Electron `43.2.0`；本地未安装 `node_modules`，本设计没有做运行时验证。

### 2.2 改造边界

本需求允许修改游戏承载、窗口布局、设置入口和相关控制链路，不借机实施以下变更：

- 不升级 Electron；
- 不把游戏页面改为第二份 guest；
- 不重写数据核心、事件账本、通知规则或代理系统；
- 不移除现有 `assets/preload/webview-preload.js` 的游戏钩子；
- 不顺带收紧整个工作台现有的 Node/remote 架构；新增的宿主页和独立窗口页面单独采用更窄的 preload bridge；
- PoC 失败时不自动切到“新建 guest 并刷新”的降级行为。

## 3. 核心不变量

实现必须通过代码结构直接维护以下约束，不能只靠调用约定：

1. `GameHostManager` 是宿主视图、宿主 WebContents、guest ID、当前父容器、窗口模式和销毁流程的唯一所有者。
2. 任意时刻最多登记一个未销毁的游戏 guest；第二个 `will-attach-webview` 必须被拒绝。
3. 普通拆出/收回只改变 `gameHostView` 的父视图和边界，不调用 `loadFile`、`reload`、`close` 或重建 guest。
4. API、档案字节和资源替换只接受当前登记 guest；迁移期间 ID 不清空、不重复登记。
5. `mg`、通知规则、系统通知、声音和推送仍只在工作台现有责任方运行一次。
6. 模式配置只在目标视图已挂载、可见且状态进入稳定态后保存。
7. 真实退出只有一个入口；宿主和 guest 的销毁幂等且有固定顺序。

## 4. 总体架构

```text
主进程
┌─────────────────────────────────────────────────────────────┐
│ GameHostManager                                             │
│  ├─ state machine / configuredMode / effectiveMode          │
│  ├─ unique gameHostView: WebContentsView                    │
│  │    └─ game-host.html                                     │
│  │         ├─ unique game <webview>                         │
│  │         ├─ subtitle / danmaku                            │
│  │         ├─ load-error overlay                            │
│  │         └─ read-only toast / launch presentation         │
│  ├─ unique gameGuestWebContentsId                           │
│  ├─ workbench parent + latest embedded bounds               │
│  ├─ detached BrowserWindow + latest detached bounds         │
│  └─ command / IPC / security / recovery / disposal          │
└─────────────────────────────────────────────────────────────┘
          │ attach one host view at a time
          ├──────────────────────────┐
          ▼                          ▼
工作台 BrowserWindow              独立游戏 BrowserWindow
├─ 顶栏、三坞、业务模块            ├─ 本地轻量工具栏
├─ 唯一 mg / 通知规则              ├─ 收回 / 刷新 / 截图
├─ #game-area 原生视图占位         └─ #detached-game-area 占位
└─ 独立模式下重排并释放游戏空间
```

独立窗口选择 `BrowserWindow` 而不是裸 `BaseWindow`，原因是它需要可访问的“收回、刷新、截图”HTML 工具栏和状态提示。窗口自身的 renderer 只负责外壳与边界上报，不加载游戏、不访问业务数据。

## 5. 模块设计

### 5.1 `GameHostManager`

建议新增 `src/main/game-host-manager.ts`，对外只暴露窄接口：

```ts
interface GameHostManager {
  start(mainWindow: BrowserWindow): Promise<void>
  requestMode(mode: 'embedded' | 'detached'): Promise<ModeSwitchResult>
  locateGameWindow(): void
  execute(command: GameCommand): Promise<GameCommandResult>
  publishOverlay(event: GameOverlayEvent): void
  getSnapshot(): GameWindowSnapshot
  dispose(reason: 'app-quit' | 'fatal'): Promise<void>
}
```

内部职责：

- 一次性创建 `gameHostView` 并加载本地宿主页；
- 把 webview 安全监听安装在 `gameHostView.webContents` 上，而不是工作台上；
- 记录且验证唯一 guest ID，并同步给 `kcs-resource`；
- 创建、恢复和销毁独立窗口外壳；
- 串行执行状态转换，提供幂等、防重入和回滚；
- 保存最后一份合法内嵌/独立视图边界；
- 路由刷新、截图、音频统计、聚焦、展示事件；
- 区分工作台 renderer、宿主 renderer 和 guest 的崩溃；
- 在真实退出时显式关闭 guest 与宿主 WebContents。

manager 不继承 Electron 内建类，使用组合方式持有实例，便于单测状态机和替换窗口/视图适配器。

### 5.2 游戏宿主页

新增：

- `src/renderer/game-host.html`
- `src/renderer/game-host.ts`
- `src/main/game-host-preload.ts`

页面结构：

```html
<main id="game-host">
  <div id="game-wrapper">
    <webview id="game-webview"></webview>
    <div id="voice-danmaku"></div>
    <div id="voice-subtitle"></div>
    <div id="lg-toasts"></div>
    <div id="game-following-effects"></div>
  </div>
  <div id="game-overlay">…</div>
</main>
```

宿主页只负责：

- 创建唯一 `<webview>` 并监听加载状态；
- 按自身可用空间把 `#game-wrapper` 以 `1200:720` 等比包含，背景留黑边；
- 对 guest 设置缩放并执行现有 `window.align()`；
- 展示工作台送来的字幕、弹幕、toast 和纯视觉效果；
- 把 toast 跳转/关闭等用户意图回传工作台；
- 把 guest 加载失败和 DOM 就绪状态报告给 manager。

宿主页通过 preload bridge 获取一次只读 bootstrap（主页 URL、可信游戏 preload URL、清洗后的 User-Agent），并在 `<webview>` 加入 DOM 前一次性设置现有安全属性。bootstrap 的路径和值由主进程生成，renderer 不能回传或覆盖可信 preload 路径。

宿主页不读取 `mg`、不初始化模块、不执行通知规则、不写配置、不发系统通知或推送。其 `webPreferences` 使用 `nodeIntegration: false`、`contextIsolation: true`、`webviewTag: true`，只通过 `game-host-preload` 暴露白名单 IPC。

### 5.3 独立窗口外壳

新增：

- `src/renderer/game-window.html`
- `src/renderer/game-window.ts`
- `src/main/game-window-preload.ts`

窗口标题为“kuma · 游戏”，`setMenu(null)`，不设置 `parent`，确保任务栏可独立切换。页面只包含：

- “收回工作台”；
- “刷新”；
- “截图”；
- 当前切换/错误状态；
- `#detached-game-area` 原生视图占位。

`gameHostView` 覆盖占位区域，不覆盖工具栏。工具栏按钮通过 preload bridge 发固定枚举命令，不允许传入任意脚本或路径。

### 5.4 工作台客户端

建议新增 `src/renderer/game-window-client.ts`，封装工作台侧的：

- 状态订阅和首屏状态拉取；
- “拆出、收回、定位”命令；
- `#game-area` 的边界上报；
- 内嵌/独立布局 class 切换；
- 展示事件发送与 toast 动作回收；
- 控制按钮的禁用、文案和焦点恢复。

这样 `src/renderer/index.ts` 不再直接知道 guest DOM 或 guest API。

## 6. 状态模型

### 6.1 状态定义

```ts
type GameHostPhase =
  | 'BOOTSTRAPPING'
  | 'EMBEDDED'
  | 'DETACHING'
  | 'DETACHED'
  | 'ATTACHING'
  | 'RECOVERING'
  | 'DISPOSING'

interface GameWindowSnapshot {
  phase: GameHostPhase
  effectiveMode: 'embedded' | 'detached'
  configuredMode: 'embedded' | 'detached'
  hostWebContentsId: number | null
  guestWebContentsId: number | null
  requestId: number
  canRetry: boolean
  error?: { code: string; message: string }
}
```

`configuredMode` 是最后一次成功持久化的用户选择，`effectiveMode` 是当前实际父容器。启动恢复独立模式失败时，允许暂时出现 `configuredMode=detached`、`effectiveMode=embedded`：应用回退到可用内嵌态，但不把一次环境故障覆盖成用户的新选择。

### 6.2 合法转换

```text
BOOTSTRAPPING ──ready──> EMBEDDED / DETACHED

EMBEDDED ──detach──> DETACHING ──commit──> DETACHED
   ^                    │
   └──────rollback──────┘

DETACHED ──attach──> ATTACHING ──commit──> EMBEDDED
   ^                    │
   └──────rollback──────┘

任一稳定态 ──宿主/guest 故障──> RECOVERING ──恢复──> 原稳定态
任一状态 ──真实退出──> DISPOSING
```

规则：

- 请求目标等于稳定态时直接返回成功，不操作视图；
- `DETACHING` / `ATTACHING` 中相同 `requestId` 只执行一次，其余切换请求返回 `BUSY`；
- 每次转换持有单一 Promise 锁，窗口 `close`、设置、顶栏和托盘不能并发改父容器；
- 只有 `commit` 后更新 `effectiveMode` 并持久化用户发起的目标模式；
- 回滚失败才进入 `RECOVERING`，该状态禁止自动新建第二个 guest。

## 7. 关键时序

### 7.1 启动

1. 主进程创建工作台和 `GameHostManager`。
2. manager 创建 `gameHostView`，先安装导航、弹窗、webview attach 和崩溃监听，再加载 `game-host.html`。
3. 宿主页创建唯一 webview；`did-attach-webview` 后 manager 登记 guest ID，设置资源识别 ID，并安装现有 preload 兜底、外链和文件导航限制。
4. 工作台完成布局后上报 `#game-area`；独立窗口外壳加载后上报 `#detached-game-area`。
5. 无配置时挂到工作台。配置为独立模式时先准备独立目标，再直接挂到独立窗口。
6. 目标准备失败时使用工作台内嵌态并提示错误，不覆盖已保存的独立模式。

宿主页和游戏 guest 的创建不等待 `mg`、矿脉或模块装配，保持当前“游戏尽早开始加载”的启动特性。

### 7.2 拆出

```text
工作台点击拆出
  → manager 校验 sender / 参数 / 当前状态
  → phase = DETACHING，禁用切换入口
  → 创建隐藏的独立 BrowserWindow
  → 等待独立 shell dom-ready + 合法非零 target bounds
  → 从 mainWindow.contentView 移除 gameHostView
  → 添加到 detachedWindow.contentView 并立即 setBounds
  → 验证 view parent 账、host/guest ID 与 destroyed 状态
  → 显示并聚焦独立窗口
  → phase = DETACHED，通知工作台重排
  → config.set('kanso.gameWindow.mode', 'detached')
```

失败回滚：若已经从工作台移除，则用最后一份合法内嵌边界重新挂回；回挂成功后销毁独立外壳并恢复 `EMBEDDED`，配置不变。回挂也失败才进入 `RECOVERING`，保留现存宿主与诊断信息。

### 7.3 收回

1. manager 先显示/恢复工作台并发送 `ATTACHING` 状态。
2. 工作台退出独立布局，恢复 `#game-area`，用 `ResizeObserver` 上报非零边界。
3. manager 保持游戏仍显示在独立窗口，直到工作台目标就绪。
4. 从独立窗口移除宿主视图，添加到工作台并设置边界。
5. 聚焦工作台的“拆出游戏”按钮或游戏区域。
6. 确认挂载成功后销毁独立窗口外壳，进入 `EMBEDDED` 并保存配置。

收回失败时重新挂回仍存在的独立窗口，窗口保持可操作，配置不变。

### 7.4 点击独立窗口关闭按钮

独立窗口 `close` 事件在非退出状态下始终 `preventDefault()`，转成一次 `requestMode('embedded')`。只有收回成功后才由 manager 标记 `closingForAttach` 并真正销毁窗口；收回失败则窗口保持打开并显示原因。

### 7.5 工作台关闭、托盘和第二实例

- 开启“关闭到托盘”：工作台只隐藏，独立游戏窗口不隐藏、不收回；
- 未开启：工作台关闭转换为一次受控 `app.quit()`，不得等待独立窗口自己关闭；
- 托盘“退出 kuma”、系统退出：先置全局 `quitting`，独立窗口的 `close` 不再转成“收回”；
- 托盘恢复或第二实例：确保工作台可见；独立模式下也恢复可能最小化/隐藏的游戏窗口，最终聚焦工作台；
- “定位游戏窗口”：只恢复、显示并聚焦独立窗口，不切换模式。

## 8. 边界、缩放与布局

### 8.1 坐标口径

`View.setBounds` 使用相对父视图的窗口坐标。工作台 renderer 上报 `getBoundingClientRect()` 得到的 CSS 坐标，主进程按该 renderer 的实际页面缩放因子换算为父视图坐标：

```text
viewX      = round(cssRect.x      × workbenchZoomFactor)
viewY      = round(cssRect.y      × workbenchZoomFactor)
viewWidth  = round(cssRect.width  × workbenchZoomFactor)
viewHeight = round(cssRect.height × workbenchZoomFactor)
```

Windows 显示器 `scaleFactor` 不再额外相乘；Electron 窗口/View 坐标已处于设备无关坐标口径，重复乘会在 125%/150% DPI 下产生偏移。该判断必须由阶段 0 的点击坐标和截图标尺实测确认。

边界消息必须满足：有限数、非负尺寸、位于发送窗口内容区内；主进程只接受工作台或独立外壳各自的 main frame。非法或过期序号直接丢弃。

### 8.2 更新频率

- 工作台与独立外壳都用 `ResizeObserver` 观察占位区域；
- 多次变化合并到一个 `requestAnimationFrame`，通过异步 `ipcRenderer.send` 上报；
- manager 每帧最多执行一次 `setBounds`，相同整数边界不重复调用；
- 分隔条松手、窗口 `resized`、最大化/恢复后补一次精确更新；
- guest `setZoomFactor` 保留约 120ms 尾随防抖，避免每帧同步跨进程调用；
- `screen.display-metrics-changed`、窗口跨屏移动和显示器拔插触发重新校准。

### 8.3 游戏比例

`gameHostView` 覆盖整个目标占位区域，宿主页内部用 `contain` 规则计算 5:3 游戏矩形：

```ts
const scale = Math.min(hostWidth / 1200, hostHeight / 720)
const width = Math.floor(1200 * scale)
const height = Math.floor(720 * scale)
const x = Math.floor((hostWidth - width) / 2)
const y = Math.floor((hostHeight - height) / 2)
```

`#game-wrapper`、字幕、弹幕、toast 和错误遮罩共享该矩形；宿主页剩余区域为黑色留边。guest 缩放只按最终游戏矩形宽度计算，确保清晰度和点击坐标一致。

### 8.4 工作台释放空间

独立稳定态下：

- 隐藏 `#game-area` 和右侧冗余分隔条；
- 保留一个中部分隔条，把左、右坞改为按原 `dockSize.left/right` 比例共同占满 `#wb-mid`；
- 只有一侧有内容时由该侧占满；折叠/空坞仍遵循现有语义；
- 底坞继续横跨全部宽度；
- 拆出前若处于专注模式，调用新增的显式 `setFocus(false)`，不使用 `toggleFocus()` 猜状态；
- 独立模式禁用专注按钮，`F9` 不改变窗口模式；收回后恢复按钮，但不自动恢复旧专注态。

该布局只增加 `.game-detached` 分支，不改变内嵌模式现有 `flex-basis` 持久化数据。

## 9. 控制与展示通道

### 9.1 游戏控制

定义固定命令联合类型，禁止字符串脚本透传：

```ts
type GameCommand =
  | { type: 'reload' }
  | { type: 'capture' }
  | { type: 'audio-stats' }
  | { type: 'focus' }
```

- `reload`：由 manager 对已登记 guest 调用 `reload()`；只允许明确用户操作或现有崩溃恢复流程调用；
- `capture`：manager 在 guest 上执行固定的 `window.capture()`，并在主进程按现有截图目录和文件名规则落盘；返回成功路径或可展示错误；
- `audio-stats`：执行固定只读表达式 `window.kansoGameAudioStats()`，供设置页和字幕时长查询；
- `focus`：先定位当前父窗口，再把焦点交给宿主/guest。

试听压音状态仍由工作台 `preview-audio.ts` 汇总，但主进程通过 manager 向当前唯一 guest 发送 `kanso:preview-audio-duck`。工作台 renderer 重载或销毁时继续强制恢复 duck，避免永久静音。

### 9.2 字幕与弹幕

`voice-subtitle.ts` 拆为两层：

```text
工作台 VoiceCaptionController
  ├─ 监听唯一 broadcaster 的 kancolle.voice
  ├─ 读取 mg / master / lode / localization
  ├─ 判定 bottom / friendly / enemy、人物、文本、色调和延迟
  └─ 发送序列化 CaptionDisplayEvent

宿主 VoiceCaptionPresenter
  ├─ 查询 manager 提供的 audio stats 或走字数时长兜底
  ├─ 维护 generation / timer / lane
  └─ 只更新宿主 DOM
```

字幕开关由工作台设置页判定并发送 `enabled/clear` 展示命令。宿主不得自行读取数据核心或重新判断战斗状态，从结构上避免两份事件消费。

### 9.3 Toast 与横幅

通知模块继续完成去重、规则路由、落账、未读、声音、系统通知和推送。只有确定需要展示在游戏画面上的结果被序列化：

```ts
interface ToastDisplayEvent {
  id: string
  severity: 'info' | 'ok' | 'warn' | 'danger'
  title: string
  detail: string
  locked: boolean
  groupKey?: string
  action?: { token: string; label: string }
}
```

宿主只负责最多四条、合并外观、TTL、锁定条和点击反馈。动作使用一次性 `token` 回传工作台，实体引用和业务跳转逻辑不下放到宿主。宿主 renderer 重载时不回放已产生的声音、系统通知或推送。

启动欢迎/点亮效果也按“工作台控制时间线，宿主只画游戏区域阶段”的方式拆分；纯工作台装饰仍留在工作台。

## 10. IPC 契约与安全

建议使用统一前缀 `game-window:*`，并集中在 manager 注册/注销：

| 方向 | channel | 发送者 | 参数/返回 | 权限 |
|---|---|---|---|---|
| renderer → main | `game-window:get-state` | 工作台、独立外壳 | 无 / `GameWindowSnapshot` | 精确 sender ID |
| renderer → main | `game-window:set-mode` | 仅工作台；独立外壳只可请求 embedded | 枚举 mode / `ModeSwitchResult` | main frame + 状态机校验 |
| renderer → main | `game-window:locate` | 工作台 | 无 | 精确 sender ID |
| renderer → main | `game-window:bounds` | 工作台、独立外壳 | surface、rect、seq | main frame + 数值/窗口范围校验 |
| renderer → main | `game-window:command` | 工作台、独立外壳 | `GameCommand` | 命令联合类型白名单 |
| host → main | `game-host:get-bootstrap` | 仅宿主页 | 无 / 只读启动参数 | host WebContents ID |
| host → main | `game-host:ready` | 仅宿主页 | 无 | host WebContents ID |
| host → main | `game-host:audio-stats` | 仅宿主页 | 固定只读查询 / 统计快照 | host WebContents ID |
| workbench → main | `game-host:overlay` | 仅工作台 | `GameOverlayEvent` | 形状、长度、枚举、频率上限 |
| host → main | `game-host:action` | 仅宿主页 | action token | token 一次性消费 |
| main → renderer | `game-window:state` | 主进程 | snapshot | 发给工作台与独立外壳 |
| main → host | `game-host:overlay` | 主进程 | 已校验展示事件 | 宿主页只读消费 |
| main → workbench | `game-host:action` | 主进程 | token | 工作台执行已有导航 |

安全要求：

1. `will-attach-webview` 监听迁到 `gameHostView.webContents`，继续校验 preload 绝对路径并覆盖所有敏感 `webPreferences`。
2. 工作台主窗口完成迁移后关闭 `webviewTag`，矿脉或业务 HTML 即使注入 `<webview>` 也无法附着。
3. `game-api-broadcaster` 从“发送者类型是 webview”收紧为“类型是 webview 且 ID 等于当前唯一 guest”。
4. `kcs-resource`、语音/立绘/BGM 档案收货口继续复用同一个唯一 guest 判据。
5. 宿主页和独立外壳拒绝任意导航，外链统一交给现有 `handleNewWindow`/系统浏览器策略。
6. 新 preload bridge 不暴露 `ipcRenderer`、`require`、文件系统、任意 channel 或任意 JavaScript 执行能力。
7. 状态快照里的 WebContents ID 只用于诊断展示，不作为 renderer 后续请求的身份凭据。

## 11. 配置与持久化

新增默认配置：

```json
{
  "kanso": {
    "gameWindow": {
      "mode": "embedded",
      "bounds": {
        "x": 0,
        "y": 0,
        "width": 1000,
        "height": 650,
        "isMaximized": false
      }
    }
  }
}
```

规则：

- `mode` 只接受 `embedded | detached`，未知值按 `embedded`；
- 新安装不写迁移脚本，默认值自然回落到内嵌；
- `bounds` 只保存独立窗口 `getNormalBounds()` 和最大化状态；move/resize 使用尾随防抖，关闭前补写一次；
- 恢复时用所有显示器 `workArea` 判断可见交集，不只判断左上角；完全不可见时按主显示器工作区居中并夹紧尺寸；
- 显示器拔出后立即把独立窗口移回可见区域；
- 运行时设置切换通过 IPC 请求 manager，设置页不得先 `config.set(mode)` 再等待结果；
- 用户选择成功才持久化；失败时 UI 回到 `effectiveMode` 并展示 manager 返回的错误。

设置页新增“游戏窗口”卡片，使用二选一控件而不是两个互不约束的布尔开关。切换中禁用，失败文案保留可重试入口。

## 12. 崩溃与恢复

### 12.1 guest 崩溃

manager 监听唯一 guest 的 `render-process-gone`：

1. 记录 `scope=game-guest`、原因、exitCode、宿主 ID、guest ID、模式和转换状态；
2. 清除资源识别 ID，进入 `RECOVERING`；
3. 仅当旧 guest 已确认销毁时，命令宿主页按现有策略创建一份新 guest；
4. 新 guest 登记完成后在原窗口模式恢复；
5. 这是明确的崩溃恢复，允许刷新/重建；不得与普通切换失败混用。

### 12.2 宿主 renderer 崩溃

记录 `scope=game-host`，与 guest 崩溃分开。先检查 guest 是否仍存在：

- guest 仍存在：保持 ID，不创建第二份 guest，尝试恢复宿主页展示层；
- guest 已销毁：进入明确恢复态，提示用户执行刷新恢复；
- 在阶段 0 未验证“宿主 renderer 崩溃时 guest 是否存活”前，不承诺自动无刷新恢复。

### 12.3 工作台 renderer 重载/崩溃

宿主由主进程持有，不随工作台 renderer 销毁。独立模式完全不受影响；内嵌模式沿用最后边界显示，工作台恢复后重新订阅状态并上报边界。通知业务恢复前不会复制第二套规则。

### 12.4 迁移失败

迁移失败只触发父视图回滚，不触发 guest crash 自愈。错误至少包含：

- `TARGET_WINDOW_CREATE_FAILED`
- `TARGET_BOUNDS_TIMEOUT`
- `REMOVE_SOURCE_FAILED`
- `ATTACH_TARGET_FAILED`
- `ROLLBACK_FAILED`
- `HOST_OR_GUEST_DESTROYED`

日志记录每次转换的 `requestId`、源/目标、各 WebContents ID、最后边界、耗时和回滚结果，便于 PoC 与线上诊断。

## 13. 退出与资源释放

引入进程级 `quitting`，托盘、工作台 X、系统退出和测试退出都进入同一个流程。`dispose()` 幂等，顺序为：

1. 状态设为 `DISPOSING`，拒绝新切换和控制命令；
2. 停止边界、窗口和 IPC 监听；
3. 从当前父 `contentView` 移除 `gameHostView`；
4. 清空 `setKcsResourceGameWebContentsId(null)`；
5. 显式关闭尚存的 guest WebContents；
6. 显式关闭 `gameHostView.webContents`；
7. 关闭独立窗口外壳；
8. 交给现有 `quit-guard` 收割仍未退出的 renderer PID。

为保证顺序，`installQuitGuard` 应接收一个同步/短时的 graceful-dispose hook：既保留其尽早安装的 `web-contents-created` PID 监听，又让业务落盘之后、OS 级强制兜底之前先执行 manager 的正常释放。

## 14. 阶段 0 PoC 设计

### 14.1 实验代码边界

PoC 单独放在 `poc/game-host-reparent/` 或测试分支，不接设置、通知、账本等业务。必须使用：

- `package-lock.json` 锁定的 Electron `43.2.0`；
- 与生产一致的宿主页 `webPreferences`；
- 与生产一致的 `<webview>` preload 和嵌套 iframe 配置；
- Windows 10、Windows 11 真机或明确记录版本的虚拟机；
- 可控本地页面模拟持续请求、音频、文本输入、canvas 截图和 iframe。

### 14.2 观测点

每次迁移记录：

- `gameHostView.webContents.id`；
- guest `webContents.id`、OS PID 和 session partition；
- `will-attach-webview` / `did-attach-webview` / `destroyed` 次数；
- `did-start-navigation`、`did-frame-navigate`、`dom-ready`、`render-process-gone`；
- 连续请求的序号、接收次数和顺序；
- 音频 `currentTime`、播放实例数和是否重新开始；
- 输入焦点元素、键盘/鼠标/滚轮命中；
- 宿主/guest 内标尺点与 Windows 实际点击坐标。

### 14.3 自动循环与故障注入

- 往返迁移 100 次，每次等待目标视图可交互后继续；
- 切换过程中持续每 50ms 产生带序号请求，断言不漏、不重；
- 音频播放中迁移，断言同一实例和进度连续；
- 100% / 125% / 150% / 200% DPI，双屏异 DPI，跨屏移动、最大化和恢复；
- 强制目标窗口创建失败、目标边界超时、`addChildView` 抛错，验证回滚；
- 分别制造宿主 renderer 和 guest renderer 崩溃，记录两者生命周期差异；
- 关闭独立窗口、正常退出和强杀宿主后检查残留进程。

### 14.4 闸门

以下任一项发生即判定核心方案失败：

- 普通迁移产生新的 guest ID、attach 事件、导航或 preload 重装；
- session、登录态、音频实例或请求监听发生中断/重复；
- 迁移后输入焦点或点击坐标无法稳定恢复；
- 目标失败时无法把原宿主无刷新挂回源窗口。

若仅边界、焦点或 DPI 问题可通过明确、可重复验证的局部修复解决，补充 PoC 记录后再放行。若 guest 被重建，则停止本方案，另立“游戏本体直接迁移为 WebContentsView”的需求与设计。

## 17. 分阶段交付

### 阶段 0：PoC

只验证嵌套 guest 随宿主跨窗口迁移的连续性。产物是可复现代码、环境记录、100 次循环日志和结论，不接业务 UI。

### 阶段 1：宿主隔离，仍只内嵌

建立 `GameHostManager` 和 `game-host.html`，先让工作台只通过原生视图显示游戏。迁移刷新、截图、音频统计、字幕和错误遮罩，确认所有现有功能等价后再继续。

### 阶段 2：双窗口迁移

加入独立外壳、状态机、边界同步、工作台释放空间、顶栏入口和设置持久化。此阶段先保证游戏连续性，不提前复制通知 UI。

### 阶段 3：业务兼容

迁移 toast/横幅、启动效果、试听压音、托盘、第二实例、崩溃恢复和退出链路。

### 阶段 4：回归与发布

完成自动化、Windows 真机、小屏、多屏、异 DPI、故障注入和退出验证。默认仍为内嵌模式；只有全部发布条件满足才展示稳定入口。

每一阶段提交都必须保持默认内嵌路径可运行，不能用后续阶段尚未完成作为当前阶段的运行前提。

## 18. 风险与待 PoC 确认项

| 风险/未知项 | 影响 | 处理 |
|---|---|---|
| 嵌套 `<webview>` 随 `WebContentsView` 重挂的生命周期无明确官方保证 | guest 重建、登录态或音频中断 | 阶段 0 硬闸门；失败后停止本方案 |
| `BrowserWindow.contentView` 子视图层级覆盖工作台 DOM | 工作台浮层被游戏遮挡 | 所有随游戏 UI 放进宿主；工作台全局浮层不得跨过原生视图 |
| UI zoom 与 View 坐标换算在异 DPI 下存在平台差异 | 偏移、裁切、点不中 | 纯函数口径 + 标尺 PoC + 四档 DPI 真机 |
| 宿主 renderer 崩溃时 guest 是否存活未知 | 无法承诺无刷新恢复 | 单独故障实验；不静默创建第二份 guest |
| 通知 toast 的交互回传跨进程 | 重复跳转或过期动作 | 一次性 token；业务动作只在工作台执行 |
| 双窗口关闭事件与托盘逻辑递归 | 无法退出、误收回、残留进程 | 全局 quitting + 单一状态锁 + 幂等 dispose |
| `setBounds` 高频调用引发卡顿 | 拖动不跟手、游戏掉帧 | rAF 合帧、相同边界跳过、guest zoom 尾随防抖 |
| 工作台独立布局改变坞位尺寸语义 | 内嵌布局配置被污染 | 独立态只派生比例，不覆盖原 dockSize |

## 19. 完成定义

设计对应的实现只有同时满足以下条件才算完成：

1. 阶段 0 的核心连续性闸门通过并保存实验记录；
2. 普通切换中宿主 ID、guest ID、session、导航和 preload 实例均不变化；
3. API、账本、通知、声音、系统通知和推送无遗漏、无重复；
4. 独立模式真正释放工作台游戏占位，专注模式语义未被复用；
5. 两种模式下现有游戏控制、字幕、代理、缓存和资源档案行为一致；
6. 切换失败可回滚且不刷新，回滚失败有明确恢复态；
7. Windows 小屏、多屏、异 DPI、焦点、休眠和拔屏验证通过；
8. 托盘、第二实例、独立窗口关闭和真实退出符合需求；
9. 退出后无 host/guest renderer 残留；
10. 默认仍为内嵌模式，未启用用户无行为变化。
